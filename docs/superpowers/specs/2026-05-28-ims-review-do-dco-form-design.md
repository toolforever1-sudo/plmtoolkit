# IMS Review — DO "Needs Change · Upload" rich DCO form

**Status:** Draft (Phase 5 follow-on to the IMS Review pilot + Phase-4 Agile write-back)
**Owner:** Vikas Jindal
**Spec sources:** ECN-129414-PROJ CRD (DO Needs-Change requirements page), in-conversation Q&A on 2026-05-28
**Related docs:**
- `docs/superpowers/specs/2026-05-18-ims-review-pilot-design.md` (Phase 1-3 pilot — DO/DM response + signed PDFs)
- `docs/superpowers/specs/2026-05-20-ims-review-agile-writeback.md` (Phase 4 — toolkit-owned Agile write-back)

## 1. Problem

The Phase-4 write-back cascade for `DO_RESPONSE_NEEDS_CHANGE` creates a minimal DCO (description + reason + IMS doc as affected item + bumped rev + auto-close relationship rule). Everything else — Priority, Product Lines, Subcontractors, Training Requirement, Approvers, Observers, Notify List, Attachment Types, etc. — DCC fills in manually after the DCO lands. That defeats the point of moving the workflow to the toolkit.

This design closes that gap by giving the DO a side-panel form that mirrors Agile's DCO cover-page fields. Required fields are validated server-side. On submit, the toolkit creates and submits the DCO fully populated, attaches the revised files with per-file Attachment Type, links the DRR, and notifies stakeholders by SMTP.

Touches **only** the DO `UPLOAD` action. `NO_CHANGE`, `NEED_HELP`, and DM responses are unchanged.

## 2. Decisions locked

| # | Decision | Rationale |
|---|---|---|
| 1 | **Drawer-style side panel** opens when DO clicks "Needs Change — Upload" action card. Replaces the existing inline `followupUpload` block. Signature + Sign & Submit live in the drawer footer. | Spec literally says "side panel on the right." Keeps the form-and-signature as one continuous action. |
| 2 | **Typeahead** for Document Owner / Approvers / Observers multi-user pickers. | Agile's `agileuser` table has 10K+ rows; pre-loading the full catalog wastes bandwidth and slows form open. Matches Agile UI's own user picker pattern. |
| 3 | **Cached bulk endpoint** on plm-agile-service for admin-list dropdowns (Priority, Product Lines, Subcontractors, Training Requirement, Business Unit, Change Impact Disposition). 1-hour TTL. | Static admin-lists change quarterly at most; first-of-the-day cost amortized across all subsequent users. Form opens sub-200ms after the cache warms. |
| 4 | **Three fixed attachment slots** — Redline Copy (1 file), Final Version (1 file), Others (multi-file). Zero attachments allowed (supports simpler OBS-request path). | Matches spec's bulleted Attachment Type list 1:1. Easier to validate than dynamic rows. |
| 5 | **Attachments land on the DCO only**, not the DRR. DRR gets a history line pointing back. | Single source of truth for revised files. Attachment Type cell is most meaningful on the DCO. |
| 6 | **Notify Stakeholders = plain textarea**, comma/newline-separated. Validated server-side at submit. | Stakeholder lists are short (3-8 entries) and typed fresh per submission. Chip UI is over-engineered for the pilot. |
| 7 | **Stakeholder notifications = toolkit-side SMTP only.** Notify Stakeholders field does NOT populate any Agile cell. | Free-text emails (external vendors) work cleanly; toolkit owns the email design; no Agile `IUser[]` resolution surprises. |
| 8 | **Two-phase submit**: pre-validate (token NOT burned) → if clean, LDAP verify → re-validate (defense in depth) → token burned → cascade. | Catches the long tail of "user typo in form" failures cheap. Token only consumed on validated input. |
| 9 | **Rollback on cascade failure**: if `create-dco-rich` fails mid-orchestration after the DCO was created, service soft-deletes the half-created DCO (`setValue(DELETE_FLAG, true)`) before returning the error. | Avoids orphan DCOs cluttering Agile from transient write failures. |
| 10 | **Reason For Change is free text** (not a dropdown). Description of Change, Reason For Change, Change Impact Details all capped at **200 chars**. | Per Vikas direction. |
| 11 | **New kill-switch** `app.ims-review.dco-form-enabled` independent of `app.ims-review.writeback-enabled`. When `false`, UPLOAD action falls back to the existing inline file+notes UI. | Enables A/B during rollout, lets us kill-switch independently if dry runs surface issues, supports local development without plm-agile-service running. |

## 4. Drawer UI layout

**Trigger:** DO clicks the "✎ Needs Change — Upload" action card on `ims-respond.html`. Drawer slides in from right. The legacy inline `followupUpload` block is removed for this action.

**Drawer shape:**
- 560px wide on viewports ≥1024px, full-width on smaller
- Page behind dims to `rgba(0,0,0,0.35)`; backdrop click → `appConfirm("Discard and close?")`
- Sticky header (eyebrow, title, `×`), scrollable body, sticky footer (username, password, Sign & Submit, banner area)

**Body section order** (each section gets a section header with `border-bottom:1px solid #E8E6DF`):
1. Disclaimer banner (warn-style callout)
2. **Auto-filled** — Number (readonly "Will be generated by Agile"), DRR Change# (readonly from token)
3. **Change details** — Priority · Description of Change · Reason For Change · Product Line(s) · Subcontractors · Training Requirement
4. **Optional details** (collapsed by default, "Show optional fields" toggle) — Business Unit · Change Impact Disposition · Change Impact Details
5. **People** — Document Owner(s) · Approvers · Observers (typeahead with chip display)
6. **Notifications** — Notify Stakeholders (textarea with hint: "Comma- or newline-separated emails and DL names. Each entry gets the auto-submit notification.")
7. **Attachments** — three fixed slots; per-file remove button on each picked file; "Others" is multi-file with `<input type="file" multiple>`

**Submit button state:** disabled until all mandatory fields filled (client-side check on every input). Disabled hover tooltip: "Fill all required fields to enable."

**Validation feedback:**
- Client-side: field-level red border + inline helper text
- Server-side (after click): field errors with `fieldKey` surface at the field; non-field errors surface in footer banner

**Progress UI:** button text cycles cosmetically every 2 sec while submit is in flight: "Validating… → Creating DCO → Attaching files (N/M) → Notifying stakeholders → Done"

**Success:** drawer closes, main page swaps to existing `successCard` with richer message:
> DCO-XXXXX created and submitted. 3 files attached. 12 stakeholders notified.

**Failure (post-validation, mid-cascade):** drawer stays open. Footer banner:
> DCO creation failed at step `<step>`. Doc Control has been notified — they will reach out. Your signed PDF is on file. Reference: corrId=`<uuid>`.

Token is already burned at this point. No retry from this page; DCC takes over.

## 6. Endpoints — contracts

### 6.1 `GET /api/ims-review/dco-form-metadata`

Pass-through to plm-agile-service. No body parameters.

**Response 200**
```json
{
  "priority": ["Urgent", "Standard", "Low"],
  "productLines": ["Client SSD", "Enterprise SSD", "HDD", "Memory", ...],
  "subcontractors": ["Subcon A", "Subcon B", "Subcon C", ...],
  "trainingRequirement": ["Required", "Recommended", "None"],
  "businessUnit": ["DCG", "CCG", "MMG", ...],
  "changeImpactDisposition": ["No Impact", "Minor", "Major"],
  "cachedAt": "2026-05-28T15:00:00Z",
  "cacheTtlSec": 3600
}
```

Errors: 503 if plm-agile-service unreachable.

### 6.2 `GET /api/ims-review/user-search?q=…&limit=20`

Pass-through. `q` ≥ 2 chars required. Server caps `limit` at 50.

**Response 200**
```json
[
  { "loginId": "asmith", "displayName": "Smith, Alice", "email": "alice.smith@sandisk.com" },
  ...
]
```

Empty array if no matches. Active users only (`inactive_flag = 0`).

### 6.3 `POST /api/ims-review/token/validate-dco-form`

**Request body** (`application/json`):
```json
{
  "token": "<uuid>",
  "form": {
    "priority": "Standard",
    "descriptionOfChange": "Updated audit checklist per ISO 9001:2025.",
    "reasonForChange": "Yearly review per CRD.",
    "productLines": ["Client SSD", "Enterprise SSD"],
    "subcontractors": ["Subcon A"],
    "trainingRequirement": "Required",
    "businessUnit": "DCG",
    "changeImpactDisposition": "Minor",
    "changeImpactDetails": "...",
    "documentOwners": ["alice.smith@sandisk.com", "bob@sandisk.com"],
    "approvers": ["carol@sandisk.com"],
    "observers": ["dave@sandisk.com"],
    "notifyStakeholders": "external@vendor.com, ims-team-dl@sandisk.com",
    "attachmentManifest": [
      { "type": "Redline", "filename": "doc-redline.docx", "sizeBytes": 124000 },
      { "type": "Final",   "filename": "doc-final.docx",   "sizeBytes": 130000 }
    ]
  }
}
```

**Response 200** (clean):
```json
{ "ok": true }
```

**Response 200** (errors):
```json
{
  "ok": false,
  "fieldErrors": {
    "approvers[1]": "carol@sandisk.com — user not found in Agile",
    "subcontractors": "Subcon Z — not a valid Subcontractor"
  },
  "formErrors": [
    "Notify Stakeholders entry 'not-an-email' is not a valid email or DL name"
  ]
}
```

Token NOT burned on either path. Activity log gets `IMS_REVIEW_DCO_VALIDATE { tokenId, ok, fieldErrorCount }`.

### 6.4 `POST /api/ims-review/token/submit-dco` (multipart)

**Multipart parts:**
- `token` — string
- `username`, `password` — AD creds for LDAP verify
- `form` — JSON string (same shape as validate-dco-form)
- `file_redline` — file (optional, max 1)
- `file_final` — file (optional, max 1)
- `file_others` — file (optional, repeated for multi)

**Server flow:**
1. Parse multipart, hydrate form payload
2. LDAP verify (existing logic)
3. Cross-check verified email matches recipient (existing logic)
4. **Re-run validate-dco-form** (defense in depth; data may differ from pre-validate)
5. Append `DO_RESPONSE_NEEDS_CHANGE` event (token burn) with full `dcoForm` + `dcoAttachmentsManifest` + `dcoFormChecksum`
6. Generate compliance PDF (existing logic, extended with "Submitted DCO request" section)
7. Call `POST /api/drr/{drr}/create-dco-rich` on plm-agile-service
8. Stamp `agileDco` / `agileSteps` on the event (in-memory + AGILE_WRITEBACK audit event)
9. Send stakeholder notification SMTP (best-effort)
10. Send DCC closure email (existing pattern, with attestation PDF)

**Response 200:**
```json
{
  "success": true,
  "dcoNumber": "DCO-00524891",
  "affectedItemRev": "10",
  "attachmentsCount": 3,
  "stakeholdersNotified": 12,
  "signedBy": "Doe, John",
  "signedEmail": "john.doe@sandisk.com",
  "pdfPath": "pdfs/2026/05/28/...pdf",
  "corrId": "<uuid>"
}
```

**Response 400** (validation rejected at re-validate):
```json
{
  "success": false,
  "error": "Form data changed unexpectedly — please reload and resubmit.",
  "fieldErrors": { ... }
}
```

**Response 500** (LDAP OK + validate OK but cascade failed):
```json
{
  "success": false,
  "error": "DCO creation failed at step 'create-dco-rich: setNotifyList'. Doc Control has been notified.",
  "corrId": "<uuid>",
  "agileErrorAt": "setNotifyList",
  "agileError": "AgileException: Notify List cell rejected value 'foo'"
}
```

### 6.6 `GET /api/agile/users/search?q=…&activeOnly=true&limit=20` (plm-agile-service)

Live SQL on `agile.agileuser`:
```sql
SELECT loginid, first_name, last_name, email
FROM   agile.agileuser
WHERE  (UPPER(first_name) LIKE UPPER(?)
   OR   UPPER(last_name)  LIKE UPPER(?)
   OR   UPPER(loginid)    LIKE UPPER(?)
   OR   UPPER(email)      LIKE UPPER(?))
  AND  inactive_flag = 0
ORDER  BY last_name, first_name
FETCH  FIRST :limit ROWS ONLY
```

Caller binds `%q%` four times. Sub-100ms on indexed columns.

### 6.7 `POST /api/drr/{drr}/create-dco-rich` (plm-agile-service)

The big one. Mirrors `DocumentReview.java:231-320` + the Phase-4 `create-dco` orchestration, extended for all the new cells + multi-attachment + addReviewers.

**Orchestration steps:**
```
1.  admin.getAgileClass(props.dcoSubclass) → IAgileClass
2.  session.createObject(class, autoNumber) → IChange dco
3.  Set cover-page cells:
      Priority(TBD), Description(1052), Reason(1053),
      Product Lines(TBD), Subcontractors(TBD),
      Training Requirement(TBD),
      Business Unit(TBD if present),
      Change Impact Disposition(TBD if present),
      Change Impact Details(TBD if present),
      Change Analyst(1099) = "Change Analyst"
4.  Document Owner(s) cell (TBD) ← resolved IUser[]
5.  AffectedItems.createRow(imsDoc)
      → set Old Rev(1056) + New Rev (bumped via RevBumper from Phase-4 spec)
6.  Relationships.createRow(drr)
      → set rule: control = DCO@Implemented, affected = DRR@Implemented
7.  drr.setValue(1575, dco.getName())  // DCO Number cell on DRR page 3
8.  For each attachment file:
      attachments.createRow(file)
      → setValue(ATT_ATTACHMENTS_ATTACHMENT_TYPE, type)
9.  dco.addReviewers(currentStatus, approverGroups, observerGroups, null, false, comment)
10. dco.changeStatus("Submitted", ...)
11. drr.send([], "DCO-XXXXX created via PLM Toolkit IMS Review write-back")
```

**Per-step logging:** every step emits one `[AGILE-WRITE]` log line tagged with the request's `corrId` (X-Toolkit-Action-Id header). Matches Phase-4 logging contract.

**Rollback:** if any step after #2 fails, the service catches, logs, calls `dco.setValue(ATT_GENERAL_INFO_DELETE_FLAG, true)` to soft-delete the half-created DCO, and returns 500 with the step name + Agile error.

**Response 200** (success):
```json
{
  "ok": true,
  "dcoNumber": "DCO-00524891",
  "newRev": "10",
  "attachmentsAttached": 3,
  "approvers": 1,
  "observers": 1,
  "documentOwners": 2,
  "submitted": true,
  "currentStatus": "Submitted",
  "corrId": "<uuid>",
  "stepsOk": ["createChange", "setCoverPage", "setDocumentOwners", ...]
}
```

**Response 500** (rollback succeeded):
```json
{
  "ok": false,
  "agileErrorAt": "setNotifyList",
  "agileError": "AgileException: ...",
  "rollback": "ok",
  "stepsOk": ["createChange", "setCoverPage"],
  "corrId": "<uuid>"
}
```

**Response 500** (rollback failed — orphan DCO):
```json
{
  "ok": false,
  "agileErrorAt": "setNotifyList",
  "agileError": "...",
  "rollback": "failed",
  "rollbackError": "could not soft-delete: ...",
  "orphanDco": "DCO-00524891",
  "corrId": "<uuid>"
}
```

## 8. Queue-event shape changes

`ImsReviewQueueStore.Event` adds three fields:

| Field | Type | Purpose |
|---|---|---|
| `dcoForm` | `Map<String, Object>` | Full submitted form payload, jsonified. Captures intent for audit even if Agile rejects. |
| `dcoAttachmentsManifest` | `List<Map>` | `[{filename, type, sizeBytes, sha256}]` — for replay-from-disk |
| `dcoFormChecksum` | `String` | SHA-256 of the normalized form payload — printed on the compliance PDF to bind the PDF 1:1 to the exact form the DO signed |

Existing fields reused: `agileCorrId`, `agileDrr`, `agileDco`, `agileSteps`, `agileError`, `agileErrorAt`, `pdfPath`, `pdfSha256`, `verifiedSamAccount`, `verifiedDisplayName`, `verifiedEmail`, `verifyIp`.

## 9. Compliance PDF additions

The existing `ImsReviewPdfService.generate(...)` is extended with a new "Submitted DCO request" section for the rich-form path. Renders:
- Field-by-field listing of every form value the DO submitted
- `dcoFormChecksum` printed in the provenance footer

An auditor reading the PDF can:
1. Pull the matching event from `queue.jsonl` by SEND token UUID
2. Normalize the `dcoForm` and hash it
3. Confirm the hash matches `dcoFormChecksum` in the PDF — proves the PDF reflects exactly what was signed

## 10. Activity log additions

New event types in `activity-log.jsonl`:

- `IMS_REVIEW_DCO_VALIDATE` — `{tokenId, ok, fieldErrorCount}` (no PII)
- `IMS_REVIEW_DCO_FORM_SUBMIT` — `{tokenId, dcoFormChecksum, attachmentCount, totalBytes}`
- `IMS_REVIEW_DCO_CREATED` — `{tokenId, corrId, dcoNumber, drrNumber, affectedItemRev, attachmentCount}`
- `IMS_REVIEW_DCO_FAILED` — `{tokenId, corrId, drrNumber, agileErrorAt, agileError}`
- `IMS_REVIEW_STAKEHOLDER_NOTIFY` — `{tokenId, corrId, dcoNumber, recipientCount, ccCount, ok}`
- `IMS_REVIEW_STAKEHOLDER_NOTIFY_FAILED` — same fields, `ok=false` + error message

## 11. Failure handling matrix

| Failure point | DO sees | DCC sees | Token state | Manual recovery |
|---|---|---|---|---|
| Validate finds field errors | inline field/form errors in drawer | nothing (validate is silent) | live | DO fixes + retries — no DCC involvement |
| LDAP verify fails | "Invalid credentials" inline | nothing | live (`tokenFailCounts` +1; lock after 5) | DO retries with correct password |
| LDAP OK but email ≠ recipient | "This link was sent to <X> — sign in as that person" | nothing | live | DO uses correct AD account |
| Re-validate inside submit fails (tamper attempt) | "Form data changed unexpectedly — please reload" + drawer disabled | nothing | live | DO reloads, redoes form |
| plm-agile-service unreachable | "DCO creation service is temporarily unavailable" banner | nothing | live (event NOT appended yet) | DO retries later, or DCC reaches out |
| `create-dco-rich` returns 500 (rollback succeeded) | "DCO creation failed at step `<step>`. Doc Control notified. Reference: corrId=…" | red row + email with corrId + the form payload | burned | DCC creates DCO manually using the form payload from queue.jsonl, then closes the row |
| `create-dco-rich` returns 500 (rollback failed — orphan DCO) | same DO message | red row + email explicitly flagged "orphan DCO may exist: DCO-XXXXX" | burned | DCC deletes orphan + creates fresh DCO + closes row |
| Stakeholder SMTP fails post-cascade | success page still shows (DCO was created OK) | separate alert email "stakeholder notification failed for DCO-XXXXX" | burned | DCC sends notification manually |

## Appendix B — Notify Stakeholders token regex

```
Email:   ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$
DL hint: (^pdl-)|(^ims-)|(^dl-)|(-dl$)   (case-insensitive)
```

A token is accepted if it matches the email regex OR the DL hint. Anything else returns a server-side field error. Tightenable later if DCC reports false positives/negatives.
