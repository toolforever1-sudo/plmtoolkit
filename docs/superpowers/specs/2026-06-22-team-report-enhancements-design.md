## 1. Background

The Team Report is a monthly PLM activity report, broken down by PCM (program/change manager),
generated by rolling the prior month's workbook forward and enriching it with AI analysis. It is
surfaced three ways:

- **In-app viewer** — the Team Report sub-tab under ECN Report
  (`src/main/resources/static/teamreport-inapp.js`), backed by
  `controller/TeamReportController.java` at `/api/team-report/*`.
- **Excel workbook** — produced by the server-only Python engine
  `data/team-report/build_team_report.py` (gitignored runtime; the working copy lives at
  `~/Documents/plm-toolkit 2/data/team-report/`).
- **PowerPoint deck** — `data/team-report/team_report_pptx_generator.py` using
  `Pcm_Workload_Template.pptx` / `Sandisk_PPT_Template_v3_1.potx`.

### 1.1 Critical architecture facts (validated against the live artifacts)

1. **`build_team_report.py` cannot create Excel charts.** openpyxl can't round-trip charts, so the
   script preserves chart XML from the prior-month file and restores it after save
   (`restore_charts_from_source()`), patching only the pivot-chart month title. **New native Excel
   charts must be seeded once into a master template, wired to fixed named data ranges, and carried
   forward by the existing restoration plumbing.** This "template-seeded" mechanism (approach **A1**)
   is already how the workbook's current 10 charts work — so extending it is low-risk, not novel.
2. **Most monthly charts already exist.** The current May-2026 workbook has **15 sheets and 10
   native charts**, including the Volume-by-PCM combo (`chart8`), Volume-by-Month combo (`chart9`),
   and the Change-Activities pie (`chart10` + `Monthly Change Activities` pivot). Several of
   Noraida's mockups are screenshots of charts that already ship.
3. **The PPTX deck already scaffolds most of item #10.** `Pcm_Workload_Template.pptx` has 15 slides
   including slide 5 (Change Activities), 6 (Volume by Month), 7 (Volume by SDSM PCM), 8 (Volume by
   Month FY26), and **slide 9 "Product Line Support by SDSM PCM (2014-2026)"** — i.e. the multi-year
   cut already has a deck placeholder.
4. **Per-PCM aggregation already works.** `ACTIVE_PCM_MAP` defines the 6 active PCMs; the engine
   aggregates `(pcm, change_type, month)` and `(pcm, month)` from the `Raw data-affected item` sheet.
5. **Change-Activities categorization is data-ready.** The 7 categories
   (Part/BOM Change, New Part/BOM Creation, Lifecycle/Status Change, Firmware/Test, New SKU Creation,
   Supplier Change, Data Alignment) resolve via the `Classification Change Type` lookup sheet
   (raw col P → col Q VLOOKUP). The pie is an aggregation of col Q.
6. **Local testing limit:** the Python engine and generated workbooks live only in the local server
   copy (`~/Documents/plm-toolkit 2/...`), not in the Mac repo and not reachable by the Agile SDK.
   Java/JS changes are testable locally against snapshot data; Python-engine changes must be
   hand-verified against the local server copy and deployed by Vikas.

### 1.2 Decisions locked during brainstorming

- **Render target:** all three surfaces — native Excel charts (A1, template-seeded) **and** in-app
  viewer **and** PPTX.
- **Scope/phasing:** one comprehensive spec covering all 11 items (build order is internal, below).
- **Excel chart mechanism:** A1 (template-seeded native charts), **not** A2 (matplotlib images).
- **Historical seed (§4):** seed 2014–2026 history from Noraida's existing workbook data; no Agile-DB
  historical query.
- **Per-PCM AI (#10):** a new layer alongside the existing per-Program-Team AI cards, not a replacement.

## 2. Goals & non-goals

**Goals**

- Deliver all 11 of Noraida's items across the three surfaces, reusing existing charts/data where
  they already exist rather than rebuilding.
- Add Quarter and Year aggregation views to the PCM table (in-app + Excel).
- Add the multi-year (2014–2026) historical charts (#5, #8) via a one-time historical seed that is
  cheap to roll forward each month.
- Add a per-PCM AI workload-analytics layer (#10) and AI report-improvement suggestions (#9),
  distinct from the existing per-Program-Team analysis.

**Non-goals**

- No rewrite of the rollforward engine or switch of charting library.
- No change to the Volume Report / `ChangeSearchService` SQL — the history is seeded from Noraida's
  existing data, so no new historical query is introduced.
- No new PCM attribution source — the 6-PCM `ACTIVE_PCM_MAP` stays authoritative.
- No automotive/credential data in any rendered output (per project security rule).

cards.** The two analyses coexist (per-Program-Team and per-PCM), kept visually and structurally
distinct so they don't get conflated.

## 4. The historical-data subsystem (seeded from Noraida's existing data)

Items #5, #8, and #10's YoY need 2014–2026 history that the monthly rollforward workbook does not
contain. **Decision: seed the history from Noraida's existing workbook data — do NOT query the Agile
DB for 2014–present.** Her workbook already carries the historical yearly figures (the source of the
2014–2026 mockups, image009/image010); we treat them as authoritative reference data, exactly like
the existing `Program Team` and `Classification Change Type` lookup sheets. This removes the only
heavy lift: there is no org-wide historical query, no 778K-row scan, and no performance guard needed.

Design:

- **Carried-forward `Yearly History` sheet.** A new workbook sheet holding **year × change-type ×
  product-line** (and **year × PCM**) totals, populated once from Noraida's existing data and then
  carried forward unchanged by the rollforward (same mechanism as the other lookup sheets).
- **Current-year upkeep only.** Each monthly run recomputes just the **current year's** row(s) from
  the data already being aggregated for that month — never re-derives prior years. Prior years stay
  frozen as seeded.
- **In-app endpoint.** A new `GET /api/team-report/history` returns the yearly aggregates (read from
  the `Yearly History` sheet, mirrored to a JSON sidecar under `data/team-report/` so the in-app
  viewer doesn't have to re-parse the workbook on every load).

**Implementation note for the plan:** capture Noraida's existing historical figures into the seed
sheet as a one-time setup step (transcribe/import from her workbook), then the rollforward maintains
only the current year. JSON sidecar is the in-app source of truth; the `Yearly History` sheet drives
the Excel charts.

- New chart components: combo (PCM, Month), ECO/AML/MCO-by-month, Change-Activities pie, ECN-by-PL

- New endpoint `GET /api/team-report/history`.
- Extend the AI stage: per-PCM analytics pass (#10) + report-improvement pass (#9), persisted to the
  analysis sidecar and returned in the data payload.

- No change to positional XLSX parsing beyond reading the new `Yearly History` sheet.

### 5.3 Excel engine (`build_team_report.py`) — server-only

- A1 template work: seed new charts (#4 monthly split, #5 yearly, #7 ECN-by-PL, #8 yearly ECN-by-PL)
  into the master template once, then extend `restore_charts_from_source()` to carry them.
- New `Yearly History` sheet writer + carry-forward.

### 5.4 PPTX (`team_report_pptx_generator.py`) — server-only
- Confirm slides 5–9 series match the finalized data; wire slide 9 (2014–2026) to the new yearly
  aggregates; add per-PCM workload analytics + AI suggestions content.

## 6. Build order (within this one spec)

1. **Foundation** — `Chart Data` scaffold + Quarter/Year aggregation (unblocks #1–#4, #6, #7).
2. **Data-ready charts & toggles** — #1 (table toggles), #2/#3/#6 (in-app rendering of existing),
   #4 (new monthly split, all surfaces), #7 (Excel chart over existing PL sheet, in-app).
3. **Historical subsystem** — seed `Yearly History` from Noraida's data (one-time) + carry-forward +
   `/history` endpoint → #5, #8.
4. **AI layer** — #10 per-PCM analytics, #9 report-improvement suggestions, across surfaces.

Each stage is independently shippable and verifiable. Stages 1–2 and the in-app/Java parts of 3–4
are locally testable; the Python-engine and PPTX parts of every stage require hand-off to Vikas for
deploy + verification on the server.

## 7. Testing & verification

- **Java/JS:** local instance at `localhost:8090` (heap ≥4g) using `plmadmin` login; exercise the

- **Python engine:** run `build_team_report.py` against the local server copy

  layout and confirm charts survive `restore_charts_from_source()`.

  pre-existing 10 charts plus the new ones render and bind to live ranges.
- **No-secrets check:** confirm no credentials/automotive data in any generated output or test email.

## 8. Risks

- **A1 template fragility** — positional ranges must stay stable; a layout shift silently breaks a
  chart binding. Mitigate with a post-generate chart-count/-binding assertion.
- **Seed accuracy** — history is transcribed/imported once from Noraida's workbook; a bad import
  silently skews every yearly chart. Validate seeded totals against her figures before go-live, and
  keep prior years frozen so a monthly run can't corrupt them.
- **Local un-testability of Python/PPTX** — every engine change is verified on the local server copy
  and deployed by Vikas; budget review cycles for that.
- **Per-PCM vs per-Program-Team grain** — #10 introduces a second analysis grain; keep the two
  analyses clearly separated to avoid confusing the existing per-team cards.
