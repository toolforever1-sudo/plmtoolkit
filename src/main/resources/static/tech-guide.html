1. Architecture Overview

The PLM Toolkit is a Spring Boot application with an embedded web server that provides a single-page web UI backed by REST APIs.

Technology Stack

ComponentTechnology
BackendSpring Boot 2.x with embedded Tomcat
LanguageJava 11+ (runs on JRE 17)
DatabaseOracle (3 datasources: primary Agile, custom BOM, Agile schema for change history)
Agile Lookup MicroserviceJava 8 microservice on port 8081 (Agile SDK API proxy)
AuthenticationLDAP / Active Directory
FrontendVanilla HTML/CSS/JavaScript (no framework)
Excel ExportApache POI (SXSSFWorkbook for large extracts)
EmailJavaMail (SMTP)

Three-Datasource Architecture

The application connects to three separate Oracle schemas:

  • Primary Agile schema (spring.datasource.*): Provides access to the item_history and item tables for field change tracking (Field Changes tab).
  • Custom schema (custom.datasource.*): Provides access to bom_extract, item_extract, and item_desc tables for the BOM Explorer and Part Extract tabs.
  • Agile schema (for Change History): Provides access to revision and change order tables in the AGILE schema for the Change History tab.

Agile Lookup Microservice

The Agile Lookup tab proxies requests to a separate Java 8 microservice running on port 8081. This microservice uses the Agile SDK to query live field values. The main application communicates with it via the agile.service.url property. The microservice must be running for Agile Lookup to function.

3. Database Connections

Agile Schema (Field Changes and Part Extract)

The primary datasource connects to the Agile PLM Oracle schema. Two key tables are used:

  • item_history: Contains field-level audit records with item number, field name, old value, new value, user, timestamp, and revision.
  • item_extract: Contains part master data with dozens of configurable columns representing PLM attributes.

Custom Schema (BOM Explorer)

The custom datasource connects to a separate Oracle schema that contains BOM relationship tables. This schema provides parent-component relationships with quantities, reference designators, find numbers, and component metadata.

Note: Both datasources use Oracle's JDBC thin driver. Connection pooling is managed by HikariCP (Spring Boot default). The pool sizes can be tuned via spring.datasource.hikari.* and custom.datasource.hikari.* properties.

4. LDAP / Active Directory Authentication

Authentication is a two-step process:

  1. User bind: The application attempts to bind to AD using the user's credentials (username@domain) to verify the password.
  2. Service account lookup: A service account then searches the directory for the user's full profile (display name, email, group memberships via memberOf attribute).

SSL/TLS

The application uses a custom TrustAllSSLSocketFactory for LDAP connections, which accepts all server certificates. This is suitable for internal corporate environments where the AD certificate may not be in the default Java truststore.

Credential Caching (Offline Fallback)

After a successful AD authentication, the user's credentials are cached in memory (password stored as SHA-256 hash). If AD becomes unreachable on a subsequent login attempt, the cached hash is checked to allow offline access. Cache is in-memory only and cleared on application restart.

Important: The credential cache does not store group membership. Users authenticating from cache will not have admin status (isPlmAdmin will be false).

5. DL Group Access Control

Access to the application is controlled via AD distribution list (DL) group membership.

Required Groups

The ldap.required.groups property defines one or more group names (comma-separated). A user must be a member of at least one of these groups to log in. Group names are compared case-insensitively.

Admin Group

Membership in pdl-plm-admin grants admin status. This controls visibility of the Tech Guide link in the navbar. Admin status is stored in the HTTP session and returned via the /api/auth/session endpoint as isPlmAdmin.

6. Access Request Workflow

Users not in the required AD group can submit a self-service access request from the login page.

How It Works

  1. User submits their name and email via /api/auth/request-access.
  2. The request is saved to ./data/access-requests.json and an email is sent to the PLM admin team.
  3. The AccessRequestService polls LDAP every 10 minutes to check if pending users have been added to the required AD group.
  4. Once detected in the group, the user receives a confirmation email and the request is removed from the pending list.

Data File

Pending requests are stored in ./data/access-requests.json. This file is read/written by the service and must persist between deployments.

Important: If the ./data/ directory is deleted or not mounted, pending access requests will be lost and users will not receive confirmation emails.

7. Email Configuration

The application sends Excel reports via email using JavaMail and SMTP.

SMTP Setup

Configure the SMTP server in application.properties. For internal corporate SMTP servers that do not require authentication, only host, port, and from address are needed.

Auto-Zip for Large Attachments

When the generated Excel file exceeds 5MB, the application automatically compresses it into a .zip archive before attaching to the email. This prevents email delivery failures due to attachment size limits.

8. Caching Strategy

Field Changes (Delta Refresh)

Field change queries hit the database directly. However, if the database becomes unreachable, the most recent query results are served from an in-memory cache. A banner is displayed to users indicating the data staleness with the "as of" timestamp.

BOM Explorer (Query Cache)

BOM queries are executed live against the custom Oracle schema. Results for individual item explosions/implosions may be cached briefly to avoid redundant queries during batch operations (when processing a file upload with many items).

Part Extract

The available column list is cached after the first load. Part search queries are executed live against the database.

9. Scheduled Reports

The ScheduledReportService manages recurring report execution for the Field Changes tab.

How It Works

  • Users create schedules via POST /api/schedules with search criteria, frequency (daily/weekly), and time (30-minute intervals).
  • Schedules are persisted to ./data/scheduled-reports.json.
  • A Spring @Scheduled task runs every 5 minutes, checking for any schedules that are due.
  • When a schedule fires, the service executes the saved search, generates an Excel report, and emails it to the user.
  • If the search returns 0 results, no email is sent (the run is logged).

Data File

./data/scheduled-reports.json stores all user schedules. The file is read at startup and written on every create/delete.

10. BOM Extracts

Daily Full CSV Extract

The BomExtractService generates a complete BOM database dump as a compressed CSV file daily at 2:00 AM (server time). The file is stored in ./data/extracts/.

  • Triggered automatically by a @Scheduled cron task.
  • Can also be triggered manually via POST /api/bom/full-extract-trigger.
  • Status check: GET /api/bom/full-extract-status returns file size, date, and generation state.
  • Download: GET /api/bom/full-extract-download.

BOM Notes Extract (Async)

The BOM Notes extract generates an Excel file (.xlsx) of all BOM relationships that have notes. This uses SXSSFWorkbook (streaming workbook) to handle large datasets without running out of memory.

  • Triggered via POST /api/bom/bom-notes-trigger.
  • Runs asynchronously; poll GET /api/bom/bom-notes-status for completion.
  • Output stored in ./data/extracts/.
Memory: The BOM Notes extract can consume significant memory. Use -Xmx2g or higher to avoid OutOfMemoryError during generation.

11. Agile Field Names

The Agile Lookup tab's manual input mode uses a typeahead autocomplete powered by a list of Agile field names stored in ./data/agile-field-names.json.

CSV Import

Administrators can update the field name list by uploading a CSV file via POST /api/agile-lookup/upload-field-names. The AgileFieldNameService parses the CSV and writes the updated JSON file.

Data File

./data/agile-field-names.json contains the field name array. It is served to the frontend via GET /api/agile-lookup/field-names.

12. Deployment

Building

./mvnw clean package -DskipTests

This produces a self-contained JAR in target/.

Running

java -Xmx2g -jar plm-field-tracker.jar

Override properties at startup via command-line arguments:

java -Xmx2g -jar plm-field-tracker.jar \
  --server.port=9090 \
  --spring.datasource.url=jdbc:oracle:thin:@host:1521:SID \
  --ldap.url=ldaps://ad.company.com:636

JRE Compatibility

The application is built with Java 11 source/target and is compatible with JRE 11 through JRE 17. Amazon Corretto 11 or 17 is recommended.

Data Directory

The ./data/ directory must persist between deployments. It contains:

  • saved-searches.json — user saved searches
  • scheduled-reports.json — scheduled report definitions
  • access-requests.json — pending access requests
  • agile-field-names.json — Agile field name list for typeahead
  • extracts/ — BOM full extract CSV and BOM Notes extract XLSX
  • activity-log.jsonl — persistent activity log (survives restarts)
  • last-report-time.txt — timestamp of the last delta report sent
  • app-knowledge.txt — knowledge base for AI help chatbot

If deploying to a container or ephemeral environment, mount ./data/ as a persistent volume.

Health Check

After startup, verify the application is running by accessing http://host:port/login.html in a browser or curling /api/auth/session.

Memory: Use -Xmx2g for production. The BOM Notes extract uses SXSSFWorkbook for streaming, but deep BOM explosions and large extracts still require adequate heap. Using -Xmx1g may cause OutOfMemoryError during BOM Notes extraction.

13. Help Sidebar and AI Chatbot

The help sidebar provides an AI-powered conversational assistant accessible via the floating "?" button on every page.

Architecture

The chatbot uses a two-tier approach:

  1. Keyword FAQ fallback: For common questions, a keyword-based lookup returns instant answers without an API call.
  2. Haiku API proxy: For complex or nuanced questions, the request is proxied to the Anthropic Haiku model via POST /api/help/ask. The AI is provided with the application knowledge base and the user's current tab context.

Knowledge Base

The chatbot's knowledge is loaded from ./data/app-knowledge.txt. This file is auto-reloaded every 24 hours, so updates to the knowledge base take effect without restarting the application. The knowledge base contains feature descriptions, usage instructions, and common troubleshooting answers.

Tab-Aware Context

When a user asks a question, the frontend sends the currently active tab name along with the question. The AI uses this context to provide tab-specific answers (e.g., export instructions for the BOM Explorer tab vs. the Part Extract tab).

Session Handling

If the user's session expires while the help sidebar is open, the chatbot detects the 401 response and displays a friendly message with a link to the login page, rather than showing a raw error.

Conversation Reset

The conversation history is cleared automatically when the user switches tabs, ensuring the AI context stays relevant to the current view.

Configuration

ai.help.api-keyAnthropic API key. If not set, the chatbot falls back to keyword-only mode.

14. Issue Tracking

Users can report issues directly from the help sidebar with an automatic screenshot capture.

How It Works

  1. The user clicks Raise Issue in the help sidebar.
  2. The frontend uses html2canvas to capture a screenshot of the current page as a PNG image.
  3. The screenshot and issue description are submitted via POST /api/support/raise-issue.
  4. The server sends an email to the PLM admin team with the user's description, metadata (username, tab, timestamp), and the PNG screenshot as an attachment.

Endpoint

EndpointMethodPayload
/api/support/raise-issuePOSTJSON with description text and base64-encoded screenshot image

16. Delta Reports and AI Insights

The delta report is an automated summary of application activity, enhanced with AI-generated insights from server log analysis.

Schedule

Delta reports are generated and emailed automatically at 9:00 AM and 9:00 PM (server time). Reports can also be triggered manually via the Send Stats button in the admin UI or by calling POST /api/admin/send-delta-report.

Persistent Activity Log

All user actions (searches, exports, emails, logins) are logged to a persistent JSONL file at ./data/activity-log.jsonl. Unlike in-memory counters, this log survives application restarts. Each line is a JSON object with a timestamp, action type, username, and relevant details. The delta report reads entries since the last report time to compute the period's activity summary.

AI Log Analysis

When the Anthropic API key is configured, the delta report includes an "AI Insights" section generated by Claude Haiku. The AI analyzes the application's server log file (configured via app.log-file) and produces:

  • A summary of notable events and patterns
  • Prioritized error excerpts with context
  • Recommendations for attention or investigation

Email Format

The delta report email uses Markdown-to-HTML conversion for the AI insights section, producing clean formatted output. The HTML is designed to be Outlook-compatible (inline styles, table-based layout). The report includes activity counts, user breakdown, and the AI insights section.

Tracking State

The timestamp of the last report is stored in ./data/last-report-time.txt. This allows accurate delta computation even across application restarts.

18. Performance

Parallel BOM Queries

When processing batch BOM requests (multiple items from a file upload), the application processes up to 3 items in parallel to balance throughput against database load. This is controlled server-side.

Connection Pooling

HikariCP manages connection pools for both datasources. Default pool size is typically 10 connections. Tune via:

spring.datasource.hikari.maximum-pool-size=15
custom.datasource.hikari.maximum-pool-size=10

Client-Side Filtering

Column filters are applied entirely in the browser (JavaScript), so they are instant regardless of result set size. Only the initial search query hits the server.

Result Limits

Field change queries are capped at 500 rows to prevent memory exhaustion on the server and slow rendering in the browser. If results are truncated, a warning chip is displayed.

19. Troubleshooting

SymptomLikely CauseResolution
Login fails with "not in required group" User is not a member of the DL specified in ldap.required.groups Add the user to the required AD group, or update the property to include additional groups
Login fails with "Authentication server is unavailable" AD/LDAP server is unreachable and no cached credentials exist Verify network/VPN connectivity to AD server; check ldap.url is correct
"Database unavailable" banner appears Oracle database connection failed Check database connectivity, credentials, and that the Oracle listener is running
BOM Explode returns no results Item number not found in BOM tables Verify the item number exists and is an assembly (has components). Check the custom datasource connection.
Email fails to send SMTP server unreachable or rejecting connections Verify spring.mail.host and spring.mail.port; check firewall rules
Slow field change queries Large time range or broad search criteria Reduce the days-back setting; add field name or item number filters to narrow the query
Application runs out of memory Deep BOM explosion or too many concurrent users Increase -Xmx to 2g; reduce bomMaxDepth; limit concurrent batch sizes
Tech Guide link not visible User is not in pdl-plm-admin group Add the user to the pdl-plm-admin AD group and have them log out/in
Session expiry shows "undefined" in UI Session timed out and AJAX call returned 401 This is handled automatically — the UI redirects to the login page. If "undefined" persists, clear browser cache and reload.
BOM Notes extract fails with OutOfMemoryError Insufficient heap for SXSSFWorkbook processing Increase JVM heap to -Xmx2g or higher. SXSSFWorkbook streams rows but still needs memory for the full query result set.
Scheduled report not firing Scheduler polling interval missed or JSON file corrupted Check [SCHEDULER] log entries. Verify ./data/scheduled-reports.json is valid JSON. The scheduler polls every 5 minutes, so reports may fire up to 5 minutes late.
Access request not detected after user added to AD group LDAP polling interval (10 min) not yet elapsed, or AD replication delay Check [ACCESS] log entries. Wait up to 10 minutes for the next poll cycle. AD group changes may take time to replicate across domain controllers.
AI insights not appearing in delta report Log file path not configured or API key missing Verify app.log-file points to an existing, readable log file. Verify ai.help.api-key is set. Check [DELTA REPORT] log entries for errors.
Help chatbot falling back to keyword answers only Anthropic API key not set or invalid Set ai.help.api-key in application.properties. Check [AI HELP] log entries for API errors. The chatbot gracefully degrades to keyword FAQ mode when the API is unavailable.
Help chatbot knowledge seems outdated Knowledge base file not updated, or 24h reload cycle not yet elapsed Edit ./data/app-knowledge.txt with updated content. The file is reloaded automatically every 24 hours. Restart the application for immediate effect.
